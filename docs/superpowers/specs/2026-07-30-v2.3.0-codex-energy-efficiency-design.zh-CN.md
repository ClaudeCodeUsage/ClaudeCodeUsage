# V2.3.0 Codex Beta R6 能耗与并发安全设计

日期：2026-07-30
状态：已批准，进入实施

## 背景与实测

本机 Codex 数据集约为：

- 1,142 个 `sessions` / `archived_sessions` JSONL 文件；
- 约 5.0 GiB 活跃历史与 46 MiB archived history；
- VS Code global storage 中持久化 Codex 索引约 4.17 MB。

在 Codex Beta R5 中，即使 `bodyReads = 0`：

- 每次刷新仍加载完整索引；
- 扫描全部文件元数据；
- 重新执行 aggregate、deduplication 和 period coverage 计算；
- 最终无条件把完整索引写回磁盘。

本机无变化刷新常见 `metadataMs = 80–105 ms`、`parseMs = 340–430 ms`；有活跃
文件时约 0.8–1.8 秒，曾出现一次约 11.6 秒的异常刷新。两个 VS Code 窗口会重复
这套工作。

R5 的原子写入固定使用 `${indexPath}.tmp`。不同 Extension Host 共享同一
`globalStorageUri` 时，会同时打开、覆盖、rename 或删除同一个临时文件。这不仅增加
I/O，也能解释此前的索引损坏。

## 目标

1. 继承 V2.2.2 的“只有前台窗口运行 recurring resources”策略。
2. manifest、时区、civil day 和迁移状态均未变化时：
   - 不读取 JSONL 正文；
   - 不重新计算 aggregate/coverage；
   - 不写持久化索引。
3. 跨 Extension Host 的 Codex refresh 在进入 load/scan/update/save 前获得同一
   index path 的单写入 lease。
4. 每次原子保存使用唯一临时文件，不允许不同进程共享固定 `.tmp`。
5. 正常、取消、失败和 stale lease 路径均释放自身 lease，不删除其他 owner 的锁。
6. 用可注入 clock 消除 period 测试对真实日期的依赖。
7. 不降低索引准确性，不读取 prompt/response/command body，不新增美元成本估算。

## 非目标

- 不创建独立 daemon。
- 不把 Codex 原始路径、session ID 或 prompt 内容写入 lock、diagnostics 或 index。
- 不取消 manifest 元数据扫描；它仍是判断文件是否变化的必要成本。
- 不用“延长刷新间隔”代替根因修复。
- 不改变 Codex token 定义、session/project identity 和 period 口径。

## 无变化快速路径

`updateCodexIndex()` 在 clone 和 derived recomputation 前检查：

1. `diffCodexManifest()` 的 `appended/truncated/replaced/moved/added/removed` 全为空；
2. `previous.coverage.complete === true`；
3. `previous.coverage.period.allTime.complete === true`；
4. 已解析时区等于请求时区；
5. `previous.coverage.period.asOfDay` 等于当前时区的 civil day；
6. 没有 contribution 处于 incomplete offset、oversized-line discard 或 stale-file 状态。

满足时返回原索引和：

```ts
{
  bodyReads: 0,
  failedFiles: 0,
  indexChanged: false,
  migration: { filePasses: 0, bytesRead: 0, pending: false }
}
```

日期跨日、时区变化、索引恢复、未完成 period migration 或 manifest 变化均绕过快速
路径。worker 仅在 `indexChanged === true` 或发生 index recovery 时保存。

## 跨进程 lease

新增 `codexIndexLease.ts`，在 `${indexPath}.lock` 上使用 `open(..., 'wx')` 原子
获取所有权。锁内容只包含：

```json
{"pid":12345,"token":"random-uuid","createdAt":1785369600000}
```

不包含原始路径、session、project 或 usage 数据。

规则：

- 默认每 50 ms 重试，最长等待 30 秒；
- 每次等待前检查 cancellation；
- owner PID 已不存在，或锁年龄超过 30 分钟时可清理 stale lock；
- `open('wx')` 后尚未写完 owner JSON 的锁有 5 秒保护期，避免另一个进程把
  正在获取中的空文件误删；超过保护期的无效锁才可恢复；
- release 前重新读取 token，只删除属于自己的 lock；
- release 遇到瞬时读取／删除错误时允许重试，不提前把自身标记为已释放；
- timeout 返回安全 `busy` 错误，保留上一份 dashboard snapshot；
- lease 覆盖 load、manifest scan、update 和 save，使后进入的 worker 能读取前一个
  worker 的最新索引并命中 no-op。

## 唯一临时文件

原子保存使用：

```text
${indexPath}.tmp-${process.pid}-${randomUUID()}
```

写入、`fsync`、close 后 rename 到目标路径。异常清理只 unlink 本次调用自己的
temporary path。即使绕过 worker lease 直接并发调用保存函数，也不会互相删除
临时文件。

## 可测试 clock

`CodexIndexUpdateOptions` 新增：

```ts
now?: () => number;
```

默认仍为 `Date.now`。period 测试显式固定在 `2026-07-22`，避免“最近7天”fixture
随着日历变化失效。快速路径测试也使用注入 clock 验证同日 no-op 与跨日 recompute。

## 验收标准

1. warm、同 manifest、同 civil day 刷新返回 `indexChanged = false`。
2. worker 在该结果下保存调用次数为 0。
3. index recovery 即使结果无变化也至少保存一次干净索引。
4. 两个 worker 对同一 index path 并发时，第二个等待第一个 release。
5. 直接并发调用 `saveCodexIndexAtomic()` 不抛出共享 `.tmp` 竞争错误，最终 JSON
   可解析且不残留临时文件。
6. 跨日和时区变化仍更新 period coverage 并写盘。
7. baseline 中日期敏感测试固定后稳定通过。
8. 完整 Node tests、UI harness tests、TypeScript compile 和 VSIX policy 通过。
