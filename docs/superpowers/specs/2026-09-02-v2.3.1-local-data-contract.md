# Claude Code Usage v2.3.1 Local Data Contract

Status: normative v2.3.1 specification. Items marked **migration input** describe legacy storage that v2.3.1 must import or clear; they are not the desired final shape.

This document is the source of truth for data read, retained, derived, displayed, exported, or sent by the extension. Any new persistent field must update this contract, its Chinese counterpart, migration and clearing logic, privacy tests, and the README privacy table in the same change.

## 1. Non-negotiable rules

1. All Section 6 local-data controls treat Claude and Codex logs as read-only source data and never delete or rewrite them. The separately opt-in Session Actions feature may move one user-selected Claude log to the OS trash only after its own exact modal confirmation; that recoverable source action is outside this clearing contract. Codex source logs are always read-only.
2. Persistent caches contain bounded aggregates, cursors, pseudonymous relationships, and minimum quota observations—not copied conversations.
3. Account identity is represented only by a stable, machine-local HMAC fingerprint. Email, display name, subscription name, raw account ID, credentials path, and reversible identifiers are forbidden.
4. Different account fingerprints are never merged into an account-level fact. If account continuity cannot be established, observations stay in an isolated unattributed epoch. A coherent epoch may still support a clearly low-confidence local-history durability estimate, but never an official account balance or invented account split.
5. Observations are facts; cost, full-quota, unused-quota, confidence, and heatmap intensity are recomputable derivatives.
6. API keys use VS Code SecretStorage. OAuth tokens, cookies, API keys, authorization headers, and unfiltered CLI output never enter configuration, globalState, Webview state, logs, exports, or indexes.
7. Network writes require an explicit user action and an exact preview of the destination and payload class. No background GitHub publication is permitted.
8. Every persisted object has a schema version, bounded retention, an idempotent migration, corruption handling, and a user-visible clearing route.
9. API-equivalent cost is an estimate at the current known API price, never a bill or a promise about subscription allowance.

## 3. Quota observation schema

P2 is an atomically written document:

```ts
interface QuotaObservationStoreV2 {
  schemaVersion: 2;
  fingerprintAlgorithm: 'hmac-sha256-v1';
  observations: QuotaObservationV2[];
}

interface QuotaObservationV2 {
  schemaVersion: 2;
  provider: 'claude' | 'codex';
  accountFingerprint: string; // machine-local HMAC or isolated unattributed epoch
  accountAttribution: 'verified-local-signal' | 'profile-continuity' | 'unattributed';
  observedAt: number;         // Unix milliseconds when the observation was received
  periodType: 'five-hour' | 'seven-day' | 'provider-scoped-seven-day';
  usedFraction: number;       // finite 0..1
  remainingFraction: number;  // finite 0..1, normalized with usedFraction
  resetAt: number | null;     // Unix milliseconds from structured evidence when available
  source: 'claude-official-api' | 'codex-local-structured-event';
  windowId: string;           // HMAC(provider, fingerprint, period, reset identity/epoch)
  providerWindowFingerprint: string | null; // HMAC of a known provider window ID; never the raw ID
  confidence: 'high' | 'medium' | 'low';
  captureReason: 'refresh' | 'reset-at-change' | 'window-id-change' | 'usage-drop' | 'profile-change' | 'migration';
  flags: Array<'approximate-boundary' | 'low-log-coverage' | 'low-price-coverage' | 'account-ambiguous' | 'clock-anomaly'>;
}
```

### 3.1 Fingerprints and account isolation

- A fingerprint is `HMAC(machineSalt, provider + stableLocalIdentitySignal + algorithmVersion)`. The raw identity signal is discarded immediately.
- A filesystem path alone identifies a local profile, not a verified account. Such observations use `profile-continuity` and cannot be merged after a detected profile/login change.
- If Codex exposes no safe stable identity signal, generate a random unattributed epoch. Never label a Codex home hash as an account. Window changes, `resetAt` changes, implausible percentage rollback, or explicit profile changes close the epoch.
- Only identical fingerprints and compatible attribution may be robustly aggregated. `unattributed` epochs never merge with one another, even when reset times coincide.
- Persistent account, provider-window, and window HMACs never enter Webview state or exports. Host projections replace them with invocation-local aliases before rendering.

### 3.2 Validation, deduplication, and atomicity

- Reject non-finite times/fractions, impossible period types, observations from the far future, and unknown free-form fields.
- Normalize fractions to 0..1 only when the source semantics are known; do not silently reinterpret arbitrary values.
- Deduplication key: `provider + accountFingerprint + periodType + windowId + observedAt + usedFraction + resetAt + source` after timestamp normalization. Exact duplicates are removed.
- Semantically unchanged polls within a short interval may compact, but each window retains first, last, pre-reset, post-reset, and anomaly observations.
- Write a sanitized temporary file in the same directory, flush and close it, then atomically rename it over the canonical file. A failed write leaves the prior valid file intact.
- Corrupt or future-schema files are quarantined with a bounded diagnostic name; no raw contents enter logs. Rebuild or migration never overwrites the only recoverable source before validation succeeds.
- A scoped provider/account clear refuses to mutate P2 when quarantined, interrupted-write, or unresolved legacy evidence cannot be attributed safely. An explicitly confirmed all-clear holds one cross-process lease, installs one valid empty canonical P2 document, and removes only exact P2 auxiliary filenames before releasing the lease; this prevents a later appender from being erased by a second delete phase.

### 3.3 Reset events and derived estimates

A reset/window boundary is detected from, in priority order: a stable provider window identifier change, `resetAt` identity change, or a significant used-fraction rollback that exceeds the configured noise tolerance. Multiple boundaries on the same day are retained as separate events. Reset events are deterministic runtime projections of boundary observations, not a second persisted fact table. Event timestamps split usage when available; day-only aggregates are explicitly approximate.

For each valid observation in one stable fingerprint/window:

```text
candidateFullEquivalent = pricedUsedEquivalentThroughObservedAt / usedFraction
```

Candidates require `0 < usedFraction <= 1`. They are robustly aggregated with weights for price coverage, log/index coverage, time-boundary quality, account attribution, and observation recency. The displayed total is never below final confirmed used equivalent. Whenever one coherent window produces a valid total, the dashboard also shows `max(full - confirmedUsed, 0)` for completed and in-progress windows, except when usage recorded after the latest observation has already overrun that observation-derived candidate; in that stale-observation case the total remains a low-confidence lower bound and unused value is withheld rather than presenting a false `$0`. Unattributed, boundary-approximate, partially priced, or locally multi-sign-in evidence remains visible but is forced to low confidence and described as a local-history durability estimate—not an official account balance. Actually overlapping quota series or competing mapped epochs still fall back to used equivalent only; no account split is invented.

Full/unused estimates are not persisted facts. They are recomputed when pricing, coverage, logs, or observation evidence changes.

## 4. Aggregation and combined heatmap semantics

All date keys use the configured data timezone. “Last 30 days” means today plus the previous 29 calendar dates in that timezone. Daily, monthly, weekly, model, effort, and grand totals must reconcile; repeated refresh/reindex must be idempotent.

The v2.3.1 combined heatmap reuses provider daily aggregates and must not rescan source logs or create a second statistics cache.

The share renderer defaults to the curated `academicViolet` palette and quantile intensity bands so isolated peaks do not flatten ordinary active days. Users may retain one of the curated palette IDs or a validated custom hex accent in P11; colors are rendering preferences, not usage facts.

```text
Claude processed = input + cache_creation + cache_read + output
Codex processed  = input_total + output_total
Combined activity volume = Claude processed + Codex processed
```

Codex cached input is already included in `input_total`; reasoning is already included in `output_total`. Neither is added twice. The combined number is a local activity volume only—not productivity, billable usage, model capability, or provider equivalence. The tooltip always exposes both provider components. Cost may be an optional view only with price-coverage disclosure.

Provider daily inputs are already deduplicated aggregates. If an identical provider/date row is nevertheless repeated at the share boundary, it is treated idempotently; conflicting values for the same provider/date fail closed and block export rather than being added together. Missing calendar dates render as zero without creating persisted facts. The activity series is bounded to 370 Codex day rows—one complete share-card year plus a boundary margin—and is reused directly from the existing provider view.

## 5. Exports, sharing, and network boundaries

- Deterministic local SVG and Markdown snippets may contain only selected date range, title, normalized daily aggregates, provider labels, totals, and explicit caveats.
- Export/share payloads must pass privacy-canary tests proving absence of account IDs, fingerprints, project/thread names, repository names, local paths, prompt/log text, and credentials.
- Optional GitHub owner/repo/path preferences are destinations, not credentials. Local sharing preview/export performs no authentication or identity/profile lookup. Only the separate publish action uses transient GitHub authentication from the VS Code authentication provider, requests `public_repo`, verifies public visibility and the default branch, previews the exact owner/repo/branch/path and create-or-overwrite action, and persists destination strings only after a successful confirmed write. Private repositories use local SVG + Markdown instead of silently escalating to broad `repo` access.
- v2.3.1 release validation uses mocked GitHub publication only. No Goal step may write to a real repository.
- AI advice requires exact request preview and a separate Send action. Quota tracking sends no local logs. Pricing refresh sends no user usage.

## 6. User controls

By G6, the Settings/Data surface and command palette must expose:

1. View local data inventory: category, location class (not a sensitive absolute path), schema, approximate size/count, oldest/newest timestamp, and possible network interaction.
2. Clear Codex derived index and rebuild it without touching source logs.
3. Clear quota observation history by provider/account epoch or all; this is irreversible but does not alter provider quotas.
4. Clear advice ledger/current and known legacy keys without clearing external accounts.
5. Reset UI state and sharing preferences independently.
6. Clear the BYOK secret from SecretStorage.
7. Clear all extension-derived data only after listing exact targets; source Claude/Codex logs and provider-owned credentials are always excluded.

Uninstall behavior is disclosed rather than assumed: VS Code may retain extension global storage until it is removed by the host/user, so the explicit clear command is the reliable deletion route.

Configuration clearing covers Global, the current Workspace, and every
currently open Workspace Folder scope. VS Code does not expose configuration
belonging only to a closed workspace; such a legacy value remains in that
workspace's settings file until the workspace is opened and the control is run
there (or the user removes it directly). The inventory and confirmation state
this host limitation instead of claiming that an unseen workspace was cleared.

Clear All is an exact-catalog operation: it removes only currently owned and
known retired names plus the two versioned legacy quota prefixes. It never
deletes an unknown/future `ccu.setting.*` key. Before any mutation, all visible
configuration scopes are preflighted. If a legacy key is present but is no
longer registered with VS Code and therefore cannot be safely updated, the
whole operation stops without deleting host state or secrets and reports the
exact key for manual removal. Activation-time owned writes are drained before
deletion, and exact global-state/file/P2 postconditions are checked afterward.

Webview-owned state is cleared only after an exact allowlist operation returns
a truthful acknowledgement. The host stores only a value-free pending client
action before requesting the reset; failure, timeout, or panel disposal leaves
that marker for idempotent replay on the next panel open. A verified
acknowledgement removes it.

## 7. Migration and release gates

- Migration order: load and validate current schema; migrate legacy quota/config values into a new temporary document; validate invariants; atomically install it; only then delete legacy plaintext/duplicate state. The P1 migration-complete marker is written only after P1 was read successfully and every resulting P2 observation was durably appended; a read/write failure remains retryable on the next activation.
- Secret migration writes SecretStorage first, then removes all explicit Global, current Workspace, every open Workspace Folder, and old globalState value. Every closed workspace is inspected when it is next opened. A workspace-only or conflicting key is never silently promoted into the one global secret slot: activation stops with fixed, localized recovery instructions and leaves plaintext recoverable. Until the user removes or reconciles that blocked legacy workspace value, it remains ordinary configuration and may remain eligible for Settings Sync. Repeat/concurrent machine-wide migration is idempotent because only identical global candidates are automatic. Other failures likewise preserve the legacy value and stop activation rather than pretending migration succeeded.
- [VS Code's extension storage documentation](https://code.visualstudio.com/api/extension-capabilities/common-capabilities#data-storage) states that SecretStorage is encrypted and is not synchronized across machines. The extension relies on the active VS Code-compatible host's SecretStorage implementation, whose concrete backing protection can vary by host. Ordinary VS Code configuration can still participate in Settings Sync according to the user's VS Code settings.
- Unknown reasoning effort is retained only when the field is missing or unrecognized. Non-zero unknown is visible and explained; zero unknown is omitted. Effort components reconcile with provider totals.
- Tests must cover old/current/future schema, duplicate observations, corruption, consecutive and same-day resets, rollback noise, account/profile changes, low price/log coverage, timezone boundaries, deterministic/private exports, and clear-data exclusion of source logs.
- G1, G3, G4B, and G5 require the specified read-only Claude CLI checkpoint. A passing review does not replace local tests or the main agent's acceptance decision.
