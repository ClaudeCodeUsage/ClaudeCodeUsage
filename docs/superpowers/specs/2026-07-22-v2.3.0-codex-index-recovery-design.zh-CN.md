# V2.3.0 Codex 损坏索引自动恢复设计（中文版）

## 背景与根因

维护者安装 V2.3.0 R4 并启用 Codex Beta 后，Codex 标签与统计仍未出现。现场证据表明：

- VS Code 已实际加载 `GrowthJack.claude-code-usage@2.3.0`；
- `$HOME/.codex` 中的 833 个用量 JSONL 可以正常发现；
- 旧的 `codex-index-v1.json` 主 JSON 结束后又残留 1,125 个字符，`JSON.parse` 报
  `Unexpected non-whitespace character after JSON`；
- worker 因索引加载失败而在扫描前返回 `files=0/0`，UI 因而把 Codex 判定为不可用。

因此，设置、原始 Codex 日志和 VSIX 版本都不是根因。缺陷位于持久索引 loader：它把可恢复的缓存损坏当成永久刷新失败。

## 方案比较

1. **只让用户手动删除或改名索引**：能立即恢复，但下一次损坏仍会复发，且普通用户难以定位 VS Code globalStorage。
2. **自动隔离并从空索引重建（采用）**：保留损坏文件供诊断，不信任或尝试拼接损坏内容；随后按现有有界 worker 流程重建。
3. **尝试截取第一个合法 JSON 主体继续使用**：可能保留更多缓存，但无法证明尾部内容不是覆盖了关键字段，恢复结果不可信。

采用方案 2。索引只是可重建缓存，宁可重新扫描，也不把部分损坏数据冒充可信统计。

## 行为设计

### 可恢复错误

`loadCodexIndex` 只自动恢复两类内容错误：

- JSON 语法错误；
- JSON 合法但 schema 不受支持。

权限错误、目录错误、磁盘 I/O 错误等仍向上抛出，不能通过“重建”掩盖真实系统故障。索引不存在继续保持现有行为：直接返回空索引，不创建损坏备份。

### 隔离与重建

发现可恢复错误时：

1. 将原索引原子改名为同目录下的
   `codex-index-v1.corrupt-<epoch>-<pid>.json`；
2. 不读取、修补或删除备份内容；
3. 返回当前时区的空 schema-2 索引；
4. worker 按现有文件数与字节预算重新扫描并原子保存新索引。

若改名失败，loader 必须失败，不能声称已经恢复。自动恢复事件只向 worker／诊断层传播安全原因码 `invalid-json` 或 `unsupported-schema`，不包含路径、原始内容或解析片段。

### 用户可见结果

- 首次成功的有界扫描完成后，即使全量回填仍是 partial，Codex 标签也应出现；
- Output 诊断增加安全的 `recovery=invalid-json|unsupported-schema|none`；
- 大历史继续使用现有 worker、取消、checkpoint、single-flight 与安静 watcher，不新增同步全量扫描。

## 测试与验收

必须先观察 RED，再实现 GREEN：

1. 复现现场的“合法 JSON 后追加尾部字符”，确认旧 loader 抛错；
2. 修复后确认原文件被改名、备份字节完全一致、返回空 schema-2 索引；
3. 不受支持 schema 同样隔离，并报告不同安全原因码；
4. 合法索引、缺失索引保持原行为；非内容类 I/O 错误不得被吞掉；
5. worker result 与刷新诊断正确传播恢复原因；
6. Node 20 全套、Linux Chromium 56 项、VSIX verifier 与 ZIP 完整性全部通过；
7. 将现场损坏文件改名备份后，验证原始 manifest 仍能发现 833 个文件，并由新索引开始重建。

## 范围外事项

- 不尝试从损坏缓存中“抢救”部分聚合；
- 不修改或读取 Codex 对话正文字段；
- 不删除用户备份；
- 不在本轮迁移明文 advice API Key。维护者应在服务商后台撤销旧 Key 并生成新 Key；后续可单独设计 SecretStorage 迁移。
